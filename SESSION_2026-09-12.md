The through-line is the opposite of yesterday's: **this session produced a lot of code and

## What is actually proven

**Break / lunch / meeting over-run reminders** (`d8dba64`). Deployed, cron healthy at
`failures=0`, and push delivery to the tablet confirmed twice with Expo receipts. A
developer on a long break now gets told — lunch once at 30 min, meeting once at 30, break
every 15 capped at 4, plus a daily budget and a workday-still-open nudge. Admins hear
nothing, per the rule already written on `kpi.nontask.block.reason`: telling admins about a
meeting is the false alarm that makes the whole feed worth ignoring.

Two design points worth keeping:

- **The cron arms nothing.** It finds whatever interval is open and derives elapsed time
  itself, so `start_break`, `switch_break`, `_set_nontask_reason`, `pause`, `pause_all` and
  `idle_reason` are all untouched and none of them can be forgotten. Switching break →
  meeting restarts the clock for free, because `switch_break` splits the row.
- **No combined total anywhere.** Concurrent timers overlap; adding them reports two hours
  of two parallel tasks as four. `_measure` exists for exactly this reason and the new code
  does not undo it.

The deploy also caught its own bug: upgrading only `369application` left `sales_test`
throwing `column res_company.break_alert_minutes does not exist`, because the Python loads
for every database on the server. Both upgraded.

## What was built and never seen run

**Home running-task card** (`21c7649`, `cab2453`). Home told a developer nothing about
their own workday once it had started — the read-only bar only renders *before* the day
opens. There is now a card with a live timer, one-tap pause through the board's own dialog,
a swipe pager when several tasks run, and arrows switching between **In Progress** and
**Today**.

Three decisions that are traps if reversed:

- **Today's number must not tick.** The server folds the running segment into
  `today_seconds`, so driving it with a clock counts that time twice. The board refuses to
  tick it for the same reason.
- **A paging `ScrollView`, not a PanResponder deck.** The deck could not use the native
  driver and had to out-race the page scroll for the responder — a fight this codebase
  already lost once in `ReorderableMenu.js:163`.
- **The 1-second clock lives in its own component.** Held at the top of `HomeTab` it
  re-rendered the entire page every second, stats grid and every tile included. That was
  the scroll stutter.

**Every native alert removed** (`3cc02ae`). 51 `Alert.alert` calls across 8 screens; there
are now none, and no `Alert` in any `react-native` import. Two treatments, not one: ~34
failures and confirms became `AppDialog` via a new `useAppDialog` hook; ~17 "you left a box
empty" became inline `FieldError` under the field, per the rule `KpiActionBoard.js:2678`
already states.

Bugs found on the way: `App.js`'s `confirmLogout` had no caller at all;
`LoginManagementScreen` imported `Alert` and never used it; and `ClientInvoices`'
adjustment checks ran in `onOk`, which `PromptModal` calls **after** `onClose` — so a blank
description threw the whole prompt away along with everything typed into it, then answered
with a banner on the screen behind.

`Reminders` and `UserManual` had the same shape: validation and save failures went through
`flash()`, whose banner draws in the screen's root view while both editors are Modals. The
message rendered *behind the backdrop* and expired unseen. Save simply looked dead.

**Reminders ring** (`707cc34`, `c5b6a00`). They never had. The screen said so and blamed
the notifee rebuild — but notifee is only needed for the *looping full-screen* alarm;
`expo-notifications` was already doing banner-and-sound for task reminders in every shipped
build. The premise was wrong and the feature was reachable the whole time.

Then extended to ring like a task alarm: same `AlarmScreen`, same full-screen takeover,
same Stop and Snooze, same ring/snooze settings and sound. The whole path was task-shaped,
so it now speaks `subject` — `{ kind: 'task' | 'reminder', id, name }` — with `asSubject()`
normalising legacy callers so the task path is untouched.

Three things that would have gone quietly wrong:

- **`next_trigger` is naive-UTC `'YYYY-MM-DD HH:MM:SS'`.** JS reads that as *local*; at
  +05:30 every reminder would have fired five and a half hours early and looked like a
  server bug.
- **`enabled` is not in `_compute_next_trigger`'s depends**, so a reminder switched off
  still carries a valid future instant. Arm on that alone and disabled reminders ring.
- **Snooze must never reach the server.** A reminder's time *is* `next_trigger`; writing
  "five minutes from now" back would turn "remind me shortly" into "this reminder is now at
  15:05", permanently, and for a repeat that means every day after. And the sync would have
  cancelled every snooze within ~15 seconds, because a snooze is exactly the
  time-mismatch the reconcile looks for.

The first two are pure functions in `utils/reminderSchedule.js` with 17 tests, because they
are the parts that fail silently.

## The build, five failures deep

1. `--device` given an adb serial instead of a device name. Mine. **Exit code 0 came from
   `tail` in a pipe** — the device's `versionName` is what exposed it.
2. **`app.notifee:core` unresolvable.** Notifee publishes it nowhere; it ships inside
   `node_modules` and expects the project to add that folder as a maven repo. Fixed as
   `plugins/withNotifeeRepo.js` (`164116b`), not a hand-edit, because `android/` is
   gitignored and regenerated — an edit there lasts until the next prebuild. It has since
   reapplied itself through two prebuilds.
3. **`android/` was stale** — generated against older dependencies, missing the
   splash-screen theme. Regenerated.
4. **Gradle daemon killed.** 6.4GB RAM, ~0.3GB free, VS Code holding 1.9GB. Not a project
   problem.
5. **EAS, during configuration**: `'android.defaultConfig.versionName' is not defined` on
   `:expo-task-widget-bridge`, alongside `Autolinking is not set up in settings.gradle`.
   One cause, two messages, and neither says what is actually wrong.

   The local module added on 11 Sep (`bbd65a9`) applies `expo-module-gradle-plugin` and
   declares only a namespace. The plugin defaults `canBePublished = true`, so in
   `afterEvaluate` it builds a maven publication and demands a `versionName` that a module
   nobody publishes has no reason to own. Every shipped Expo module declares one;
   `node_modules/expo` instead sets `canBePublished false`, which is what this module now
   does too.

   The autolinking line is a red herring: `expo/android/build.gradle:10` applies the
   autolinking plugin inside a `try/catch`, so the subproject blowing up is swallowed and
   resurfaces as a settings.gradle complaint. The tell is the module list — the legacy
   fallback prints eight dev-client modules, real autolinking prints twenty-six. And
   `:expo-task-widget-bridge` existing as a Gradle project at all proves autolinking ran,
   since only Expo autolinking can find something under `modules/`.

   Worth knowing: this was the **first cloud build since that module was added**. A local
   module is exercised by nothing else — not jest, not Metro, not the installed APK.

**`app.json` referencing an untracked plugin** was caught before it escaped: the reference
without the file fails at config resolution on any other machine or on EAS. They are
committed together.

## Two beliefs this session overturned

**Notifee is not dead.** `services/alarm.js` and `Reminders.js` both say it no-ops "in
every currently installed build". The installed APK carries 10 notifee components, and the
device logs `NOTIFEE: received application context` with zero unavailable warnings. The
`[Alarm] notifee unavailable` line that seemed to confirm it came from **jest**, where no
native module exists. The new code therefore asks `alarmAvailable()` at runtime rather than
trusting the comment, and falls back to a banner if it ever says no.

**The tablet does load from Metro.** I concluded it could not, from a missing dev-launcher
activity, and said so more than once. Three live TCP connections to port 8081 and a
`[ReminderAlarm]` log line from code written the same day proved otherwise. **All of the JS
above is already running on that device** — only the notification icon and the notifee
plugin actually need a build.

## The notification icon

Notifications showed the generic Expo icon. Passing `icon` to `expo-notifications` is what
generates a monochrome small icon and the `default_notification_icon` meta-data pointing at
it; with no override Android falls back to `android:icon`, the coloured 369 launcher icon.
That is all `Showroom_check` does — it is not doing something cleverer, it is doing less.

Before that, the supplied 369 logo was converted to a proper white silhouette (Android
reads only alpha for a small icon; the file was 1254×1254 RGB with **zero** transparency
and would have drawn a solid white square). That work was reverted when the simpler answer
turned out to be right, but the conversion approach is recorded here: alpha from luminance
with a steep ramp, so the 3D shading does not become semi-transparent and wash out at 24dp.

## What the next session must not assume

**Nothing app-side has been watched working.** Specifically unproven, in rough order of
risk:

- **Snooze**, and that snoozing leaves the server's `remind_date` alone. Entirely new code;
  a mistake here silently rewrites a repeating reminder's schedule.
- A reminder ringing full-screen; Stop silencing it.
- The Home card: swipe pager, In Progress ↔ Today, per-task pause, the restore-where-you-
  left-off.
- 51 alert conversions and the inline validation.
- The coloured notification icon (needs a build; the config is in).

The tablet is on Metro and notifee works, so all of the JS is testable **now** without a
build. That was not true for most of this session.

And before spending another cloud build: `npx expo prebuild -p android --clean` followed by
`cd android && ./gradlew help --no-daemon` reproduces the entire configuration phase
locally in under three minutes, at a fraction of the memory a compile needs. That is where
failure 5 lived, and it would have cost nothing to catch.

Also still open, found but not chased: `RangeError: Maximum call stack size exceeded` in
the device logs. Note it fires **on modal open**, not at boot — so an earlier session note
ruled out the recursive walks on a premise that was simply wrong. Five duplicate style keys in `KpiActionBoard.js` (`title`,
`taskName`, `reasonInput`, `fieldHint`, `inputErr`) where the later definition silently
wins; and `KpiActionBoard` still carrying its own `dlg`/`say()` and inline `MeetingPicker`
now that shared versions exist.
