# Session — 9 Sep 2026

The app side of the day's Odoo work. Where something is built but not yet proven on a device, it
says so — and one substantial thing is exactly that.

The through-line: **the module gained seven things today and the app had none of them.** But the
more useful pattern underneath is narrower and it repeats — *the app was reading the wrong route.*
Progress history comes from `/kra_kpi/task/details`, not `/kpi/progress/list`, so every field
today's commits added to the latter was invisible to the app no matter how much client code was
written. That is not a missing feature, it is a missing serializer line, and it accounted for two
of the five items below.

## 1. Task board — `405f6a2`

Five of the seven web additions, ported. The sixth (a grid/list toggle) the app already had since
before today, and the seventh is the KRA Report, which is its own piece of work below.

**A second clock on a running card.** How long since the task was picked back up, and what from —
"after break", "after lunch". Nothing new is fetched for it: `timer_start_datetime` is the current
run's start and `timer_total_seconds` is everything banked before it, so **banked time plus a live
start means the task was resumed rather than started.** That inference is the whole feature, and
it is the part worth re-reading — it is why the clock correctly stays silent on a first start.
`pause_reason_code` was already being sent by both task serializers and simply never read. Eight
unit tests pin it.

**Break reasons switch in one tap.** The app had this for the *no-task* case already; the paused-
task case still meant Resume then Pause-again. That is two calls that can half-apply, and it banks
a few seconds of task time nobody worked. `/kra_kpi/break/switch` closes one break and opens the
next at the same instant. The reason already in force is filtered out of the pills — switching to
it is a server-side no-op, and a button that does nothing is worse than no button.

**Progress entries can be edited and deleted.** Gated on the server's own `can_edit`, never a rule
re-derived in the client. This needed the serializer line described above; `/kpi/progress/list` had
been given `can_edit` today and `task/details` had not.

**The activity popup splits three ways** — All / Pause log / Heading changes. "All" is served from
the details payload already in hand; the two narrower kinds fetch their own 200-row window, which
is the point: a pause log sliced out of the "all" window would quietly lose the older rows. A
rename now reads `"old" -> "new"` rather than only "Renamed" — those rows were *already arriving*
and rendering with no detail line.

**One update can carry several files.** Sent as a single request with a repeated `file` key, so an
entry never ends up holding half a set. Both size caps are checked at pick time — one oversized
file, and a set that only goes over when added to what is already staged.

Server side: `files[]` added to `task/details` on both progress and manual rows, and
`/kpi/progress/file_b64` now takes an `attachment_id`. The app **cannot** use the
`/kpi/attachment/download` route the web uses for extra files — it is `type='http'` and an app
request carries no session cookie, so it lands on the login page. Same trap as the client ZIP
download, documented on the route itself.

## 2. KRA Report — groundwork

The report is to match the web exactly, ZIP export included. The web builds its PDF, Excel and ZIP
**in the browser** with jsPDF, jspdf-autotable, JSZip and ExcelJS; the app now does the same on the
device with those four as npm packages. This was confirmed as still the intended architecture by
`kpi.report.download`, the model added on the Odoo side today, whose own docstring says the files
are built client-side and that it exists only to keep a copy of what was handed over.

**`utils/kraExport.js`** — all five builders ported near line-for-line. What changed is only ever
the last step of each:

| web | here |
|---|---|
| `doc.output('blob')` | `doc.output('datauristring')` → base64 |
| `doc.save(name)` | base64, caller writes the file |
| `zip.generateAsync({type:'blob'})` | `{type:'base64'}` |
| `URL.createObjectURL` + `<a>.click()` | the app's existing SAF / share-sheet save |

RN has no DOM, its `Blob` is a partial polyfill JSZip and ExcelJS will not take as binary input,
and `URL` has no blob-URL support. Base64 is the one currency every step and every save path in
the app already speaks. Helpfully, none of these builders touches canvas or embeds an image, which
is normally the hard part of such a port.

**`metro.config.js` and `shims.js` are both new and both required.** Metro maps the bare module
names `buffer` / `stream` / `process`; `shims.js` installs the `Buffer` and `process` globals and
is imported as the first line of `index.js`. Mapping alone is not enough — these libraries read
`Buffer` off the global at module scope, so without the shim the bundle builds and then throws on
the first workbook write. `shims.js` fills in only the missing `process` fields rather than
replacing the object, because RN and Expo both populate `process.env`.

**18 tests** in `utils/__tests__/kraExport.test.js` assert on the actual bytes — what is inside the
archive, and what the numbers on a per-project sheet say. Two of them pin bugs the web shipped and
then fixed, because those are precisely what a port re-introduces:

- an "Excel pack" burying one workbook under a PDF per task
- a per-project sheet printing the **whole report's** totals, because the shared sheet writer
  called the report-wide helpers

**`services/kraReport.js`** wraps the three data routes. Three response-shape traps are documented
there and worth knowing before writing the screen: `/kra/generate` omits `data`/`summary`/`filters`
entirely on failure rather than sending them empty; `/kra/filter_counts` returns **maps**, not
lists, spread at the top level, whose integer keys arrive as **strings** over JSON-RPC; and the
`kras[]` option list is ordered `sequence, id`, so a parent is not guaranteed to precede its
children — build the tree by `parent_id`.

One jest config change came with this: ExcelJS bundles a copy of `uuid` that ships untransformed
ESM, so `^uuid$` is mapped to its CommonJS build. Nothing in the app imports `uuid` directly.

## What is NOT proven

**The export module has been proven under Node, not on a device.** All 238 tests pass and the three
export paths produce real PDF/XLSX/ZIP bytes, but that is jest resolving these packages, not Metro.
The remaining risk is entirely in module resolution and the `Buffer` global — which is what
`metro.config.js` and `shims.js` exist for, and what the bundle check below is for. Nobody has yet
run `npx expo export`, and no pack has been generated on a phone.

**Nothing on the Odoo side is deployed.** Repo edits do nothing until the module is copied into
`C:\Program Files\Odoo 19.0.20260119\server\odoo\addons\kra_kpi_module`, and the Python changes
need a server restart after that — an upgrade run in a separate process leaves the running server
on the old `.py`. `369application` is live, so this was deliberately left alone.

**Someone else is working in this repo concurrently.** Two commits landed mid-session (`e16d4eb`,
`2af08be`) and the working tree still holds their in-progress Odoo changes — `kpi.py`,
`kpi_report_download.py`, `kpi_download_cleanup_cron.xml`, `kpi_configuration.js`, `kpi_create.js`,
`kpi_kra_report.js` and others. **None of that is in this commit.** Check with them before touching
`odoo_modules/`.
