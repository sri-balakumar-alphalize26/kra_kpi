## The morning: the two designs from 10 Sep, built

**Lane ordering** (`337bb34`). `kra.kpi` declares no `_order`, so Odoo falls back to id ASC
and every lane read oldest-at-top. The trap — recorded in the previous session and worth
keeping — is that sorting by id DESC does not fix it: id is *creation* order, and the
complaint was about a task created months ago and worked yesterday. Only activity answers
it, and nothing in the payload carried activity.

So the server now sends `last_activity` from one `read_group` over `kpi.time.log`, using
`max(start_time)` **and** `max(end_time)`. Both, because worked A 09:00–17:00 and B
10:00–10:30 means `max(start_time)` alone ranks A as older when A was in fact touched last.

Checked against live data before and after: *"Fix customer support module"* moved from
position 14 to 2, *"[APITEST] RootOnly approver"* from 86 to 4.

**Reminders** (`a11f63d`, `bf0ab28`, `fe37a50`). Model, history, repeat rule, client/KRA
link, then the app screen. Three decisions are load-bearing and each is a trap the obvious
implementation walks into:

- The toggle is `enabled`, **not** Odoo's `active`. `active=False` filters a record out of
  every list and every `search()`, so switching a reminder off would make it **vanish**
  rather than show as off. Verified on the device: the row stays, greyed.
- Completions are their own model with the name and time **snapshotted** and
  `ondelete='set null'`. A single `done_at` remembers only the last tick. Verified: the
  history row survived its reminder being deleted.
- The repeat rule is Python and only Python. "+1 day, same wall-clock time, across a DST
  change" written twice will disagree, and the disagreement surfaces as an alarm an hour
  early months later.

**The app half needed no controller and no module change.** `callKw` reaches `kpi.reminder`
directly; the ACL already grants `base.group_user` CRUD and the record rule already scopes
rows to their owner. Proved by running the exact create / search_read / write /
action_complete / unlink calls **as a non-admin user** before writing any screen code.

## The card fixes, and a root cause that was not what it looked like

`a1aa6c2`, `145f916`. Reported from screenshots: red cards never stop being red, card text
is sliced in half, no task number visible.

**First finding: the screenshots were the WEB board, not the app.** The `Time:`/`Estimate:`
labels exist only in `kpi_action.js`. That decided where every fix went — though the colour
rule is written twice, deliberately identically, so it changed in both.

**The clipping root cause was not the obvious one.** `.kpi-task` is a fixed 292px flex
column whose children kept the default `flex-shrink: 1`, so the browser **compressed each
child in place** and the ones carrying their own `overflow:hidden` sliced their own text
mid-glyph. That is why the cut appeared in the *middle* of the card with lines still
painted below — nowhere near the fade mask that commit `935c3f8` had added for exactly this
problem. The fade was right; it never got a chance. One line (`> * { flex: 0 0 auto; }`)
sends the overflow to the real bottom edge where the mask was already waiting.

The pink cards showed it first because `.kpi-task-fresh` set a 2px border against the base
1.5px — 1px less content height under `border-box`, enough to push a line over the edge.

**The task number already existed.** `external_ref` (`TASK-014`, `REQ-012`) is generated by
`_next_ref_for_prefix`, already in the payload, already badged elsewhere — just never on the
card. Two proposed numbering schemes were declined with reasons: per-employee `001` is not
unique across employees, and first-two-letters of a name **already collides on live data**
(`AD` = Adithyan A R + Administrator, `KA` = Karthick + KarthickM).

Showing the ref meant also making it findable — the board search matched name and assignee
only. Both sides are now stripped to letters and digits, because refs store a hyphen and
nobody types one. Verified on the device: `req148` narrowed 645 → 1.

## Routes the app only half-used

`07a866a`. Found by diffing all 246 server routes against every route the app calls.

- **The review stamp was displayed and never written.** The board renders
  `coordinator_review_started_at`, but `/kpi_review/mark_started` was never called — so
  reviewing from the phone left the field blank forever. Now stamped from **both** the
  approve and reject paths, matching the web, because sending work back is still having
  reviewed it.
- **A phone-built report vanished.** `services/kraReport.js` called list / file / delete but
  never `download_save`, so the app **read from and deleted from a history it never wrote
  to.** The call goes in `runExport` and deliberately **not** inside `save()` — `save()` is
  also what re-writes a file pulled back *out* of the history, so recording there would grow
  the history by reading it.

## What device testing found that reading did not

All five of these needed the tablet.

1. **Reminders History became unreachable.** The link was gated on the list having rows, so
   deleting your last reminder hid the history — at precisely the moment it held the only
   thing left. That is the exact case the snapshot design exists for.
2. **A declined download was still filed.** `save()` returns *normally* when the Android
   folder picker is cancelled (it is an ordinary outcome, not an error), so `runExport`
   carried on and uploaded a full history row, bytes included, for a download that never
   happened. Found by an adversarial re-read, confirmed in the code.
3. **The switch dialog named nothing.** Reusing the non-task dialog for break switches
   rendered a blank "from" row and the sentence *" is saved to your Workday Map"* — it read
   `live.nontask.reason_label`, but a task break lives on `live.active_break`.
4. **That dialog had no height cap at all.** Fine as a title and a sentence; not fine once a
   meeting switch added a people list. On a phone-proportioned screen its own Confirm button
   went to the edge. Same shape as the Pause fix.
5. **The Pause dialog bug is height-dependent, and the recorded diagnosis was wrong.** See
   below.

## The Pause dialog: the previous session's diagnosis was wrong

`94d1b61`. Reported as *"Pause → Meeting → 'Who is it with?' cannot be scrolled."* The
10 Sep write-up blamed nested scrollers and noted the list *did* scroll under an adb swipe,
treating that as inconclusive.

It was conclusive. `MeetingPicker` already sets `nestedScrollEnabled` — that is why the
swipe worked. **The Pause dialog had no `ScrollView` at all**: a plain `View` inside a card
capped at 92% of screen height with `overflow: hidden`. Pick Meeting and the body grows by a
190px list plus a search box, a label, a note and two hint lines, so the tail is clipped —
**including the Confirm button**.

The user settled it: **broken on a phone, fine on the tablet.** A gesture conflict would
misbehave on both; a cap that is a *percentage* of screen height only overflows on a short
screen. That also explains why the 10 Sep device pass missed it — it ran on the SM-T510.

Six sibling modals already used `MODAL_BODY_MAX_H`. Pause and Pause-all were simply missed.

**Still not verified on a device.** See Not done.

## Meetings: the same fact recorded three different ways

`b886e7a`, `119d672`. The user noticed that "In a meeting" from the top pill never asks who.

Three places could start a meeting and **only one asked**:

| how the meeting started | asked who? | why |
|---|---|---|
| pausing a task | yes | `kpi.break.log.meeting_with_user_ids` |
| "Not on a task?" popup | **no** | `kpi.nontask.block` had no such field |
| switching a break → meeting | **no** | route accepted it; the app never sent it |

So whether a meeting remembered its attendees came down to whether a task happened to be
running at the time. The web behaved identically, so it was not app/web drift — it was a
gap in both.

Module side: `kpi.nontask.block` gained the same two fields as `kpi.break.log`. The awkward
part is that the block **row does not exist until the block closes**, so an open one lives
on `kpi.work.session` — attendees ride along there too (`nontask_meeting_with_ids`,
mirroring `nontask_note`) and are copied across at creation. They are **rewritten** on every
`_set_nontask_reason`, not merged, so Meeting → Break → Meeting cannot carry the first
meeting's people into the second.

The validator lives on the **model**, not the controller: the task-pause twin
(`_clean_meeting_ids`) sits on a different controller class the idle route cannot reach, and
copying it would have made two rules that drift.

**Proved on production.** Break log 263: `meeting_with_display = "Adithyan A R, Angitha"`.
Row 261 directly above it is a meeting switch from *before* the fix, with that column empty.

**And the two switch rows now behave the same.** They sit next to each other and looked
identical: the non-task one opened a confirm, the task-break one fired on the tap. One
dialog now serves both, told apart by `kind`.
