# Session — 10 Sep 2026 (part 2)

**App version 1.2.0** (was 1.1.0, set on 18 Aug). Third round of fixes, so the version moved with
it. It is read from `Constants.expoConfig.version` and shown in the Profile footer, so `app.json` is
the only place to change.

App-side only, except one module file. 17 commits, `7008fa1` → `7393525`, pushed to both remotes.

The through-line, and it is the opposite of last session's: **the app was worse than anyone
thought.** The 9–10 Sep work was module-only and left the app behind, so this began as a catch-up —
port the module's new features. Three audit passes later it was clear the backlog was not the
problem. The app had defects that corrupted numbers other people rely on, and defects that reported
success for work the server had refused. Those came first, and they were most of the work.

## How the audit was done, and why it took three passes

Pass one read every module commit from `37b7a2c`..HEAD and asked "does the app have this?". Pass two
compared the report and the board/workday subsystems line by line. Pass three covered the ~25 module
components and ~20 app screens the first two never touched — admin/setup, client and invoicing,
dashboards, the non-KRA reports.

Pass three found the worst things. That is worth remembering next time: the areas nobody thinks to
audit are the areas nobody has audited.

**Three findings were wrong and were corrected before any code was written**, which is the other
reason this took three passes:

- The ZIP divergence was already fixed in `2350778` — verified line-for-line, including the
  per-project TOTAL and the ISO-week year boundaries.
- The TaskDocuments multi-file suspicion was wrong. `/task_documents/details` never returns an
  entry's extra files, and the **web screen is equally blind**. A server gap, not an app one.
- Correcting a Break to Lunch or Meeting was already shipped in `405f6a2`. The audit derived that
  gap from two lines without noticing the switch row directly below them.

## 1. The app was telling Live Tracking its own users were idle

`/kpi_owner/live_tracking` decides who is "working right now" from **one** signal: how fresh
`kpi.work.session.last_heartbeat` is, against a cutoff of at least a minute. The web board has
always bumped it every 15s. **The app called that route nowhere.**

So a phone-only developer went grey a few minutes after Start Workday with a task still running, and
dropped out of the "Active now" count — on the admin's screen, not just their own. An app bug that
corrupted a number other people were reading.

Beats every 30s while the workday is open. Not through `action()`: firing all day, its two log lines
a beat would bury everything else worth reading.

## 2. Invoices created on the app were quietly leaving work out

All three task types ticked means "no type filter", **not** "these three prefixes". The server turns
any non-empty `task_types` into a hard `external_ref` prefix match, so `REQ,UPT,BUG` on the wire
drops every signed-off task whose ref is blank or carries some other prefix.

The admin ticked nine tasks, got a short invoice, and `_diagnose_empty` blamed "the REQ / UPT / BUG
filter" for a filter they never set. Worse, the picker had offered those tasks as tickable, because
`typeAllowed()` in the same file already implemented the rule correctly — the screen documented the
behaviour in a comment and then did the opposite.

## 3. Saves the server refused were reported as saved

These routes **return** `{status: false, message}` rather than raising, so `await fn()` alone cannot
tell a refusal from a success. Three screens took that as success.

Configuration flashed its green tick on all nine settings. Login Management was worse: Reset
password renders for every user including the Odoo superuser, the server refuses that unless the
caller is a system admin, and the row still flipped to **"Reset ✓"** — so everyone believed an
administrator's PIN had been reset when it had not. A refused user *list* rendered as "No users in
this role", which reads as a fact about the company rather than about the person asking.

One guard per screen now, so no saver can drift back: it checks status, rolls optimistic state back,
and reports in the server's own words where the tick would have gone.

## 4–8. The rest of the severe set

- **A sent-back task lost its answer.** Only `/task/resume_with_reason` clears
  `self_needs_resume_reason` and re-arms the admin-accept deadline. The app sent every resume down
  the plain route, so the flag stayed on and the clock stayed un-armed — the task waited on nobody,
  for good.
- **The second document on a manual downloaded the first**, saved under the second one's name. One
  dropped argument; everything around it was already correct.
- **The report ignored report-only rows and renames**, so the phone showed a smaller task count and
  a smaller grand TOTAL than the browser for the *same saved report*. The app was holding that state
  in memory and rendering as though it did not exist.
- **Owner Dashboard created a real draft invoice on one tap** where the web only prefills a form.
- **The invoice PDF** — see below.

## The invoice PDF: a correction worth recording

I first said this was not app-fixable, because the app downloads a server-rendered PDF. That was
wrong, and the module says why itself: *"this invoice has TWO renderers — this one (jsPDF, in the
browser) and `_build_invoice_pdf` in kpi_reports_api.py (reportlab, used by the mobile app). They
must agree."* They did not, and the app was downloading the wrong one.

This project had already solved that exact problem once: `utils/kraExport.js` is a port of the web's
KRA-report builders, and its header records the whole recipe. So the invoice builder was ported too,
fed by `/pdf_data` — the route the browser already uses. **No module change**, and it fixed three
separate items at once: already-billed lines dropped so the rows sum to the stated total, the
cost-free copy when "Show amounts" is off (the app had that toggle with nothing behind it), and
Overall Notes printed.

The Work Report PDF went the same way, for the same reason plus two of its own: it was rendered from
the *current* filters rather than the result on screen, so changing a preset after Generate exported
a different period than the badges showed; and "Show hours" off was applied to the list only.

**Three documents are now built on the device: KRA report, invoice, work report.**

## Where the web turned out to be the broken side

Copying the web blindly would have introduced bugs. Four times the module was checked and the web
screen was the stale one:

- **Complete on hold/rework.** The web's board does not offer it; the server's own `can_complete`
  allows those states and the web's *detail panel* offers them. The board list is stale — matching
  it would have removed a working path. The app was left alone.
- **The lane rule.** `hold`/`rework` now lane by priority, matching the module as instructed — but
  **not** the line after it. The web pushes only `if (groups[key])`, so a task whose priority is not
  a lane key appears on its board **nowhere at all**. The app's fallback keeps it. Both halves are
  pinned by tests.
- **"A week" downloads.** `_isoWeek` is defined twice in `kpi_kra_report.js`; the later
  object-returning version wins, and the dialog then compares that object to another with `===`. It
  can never match — **the web's "A week" download returns zero rows.** The app's own tested `isoWeek`
  was used instead, and a test exists purely to prove it selects something.
- **The New Task form** carried three defects that were fixed rather than copied: a KRA dropdown
  reading a key the server never sends; two non-transactional calls that leave an orphan 0h task and
  create a *second* one if you press the button again; and a "clear those filters and show it" link
  that leaves a task hidden by KRA or date range still hidden.

Ten more web/server-side problems are recorded in the plan rather than fixed here — four UTC date
bugs, the browser-clock timers, a pending queue with no role gate, and three server routes missing
authorisation checks.

## The one module change

`app_user_manual_369` had a real leak. `app.user.manual` filters by role on purpose — its docstring
says *"server-side, so a client can never see admin docs"* — and the backend went straight round it:
the ACL grants `base.group_user` read on every record with no record rule, and the menu carried no
`groups=` at all. So the User Manual list sat on **every employee's menu bar**, showing manuals
tagged Admin and Client to anyone who opened it.

The menu is now Coordinator and up, and two of the four ACL rows turned out to be dead weight —
Owner and System were each granted rights they already had through Coordinator.

**NOT DEPLOYED.** A menu and ACL change needs the module copied to the addons path and **upgraded**,
not merely a service restart. Until that happens the leak is still open.

## Decisions taken

- **Dark mode: dropped.** `theme.js` is a flat object imported directly by every screen, and each
  screen additionally hard-codes hex values throughout its StyleSheet. It means a runtime-switchable
  theme plus an audit of every screen — more code than everything else here combined.
- **Server-driven reminders: left as is.** The on-device alarm stays; a task with a configured
  reminder is silent on the phone by choice.
- **Download history: mirror the web's, read-only.** The app builds its documents on the device and
  does not post them back, so the sheet lists what the *browser* saved and says so, rather than
  letting someone wonder why the report they just built is missing.
- **Widget config lives in Profile → Preferences**, not an Android configuration activity. That
  activity buys exactly one thing — different settings per widget instance — and is a whole extra
  Activity in native code.

## The widget: root cause found, not yet fixed

Reported: the widget says "No task running" while a task is running.

**It is not a data bug.** The app writes the state file correctly within 15 seconds. A widget process
cannot run JavaScript, so that file is the entire channel — and **the app cannot ask Android to
redraw the widget**, which needs a broadcast only native code can send. Android's own auto-refresh
floor is 30 minutes. Tapping the widget refreshes it, which is why the bug looks intermittent.

A comment in `plugins/withTaskWidget.js:163` claims "the app pushes an update whenever the running
task changes". It does not, and that comment should go with the fix.

**Nothing else on the widget wish list is worth building until this is fixed** — a live-tracking bar
or a Start Work button that can be half an hour stale is worse than none. Decided approach: a small
local Expo module calling `AppWidgetManager.updateAppWidget(...)`, invoked right after the file is
written.

Reported: Pause → Meeting → "Who is it with?" cannot be scrolled.

**It scrolled under a synthetic adb swipe** — the list moved from Adithyan…Hashina to

## 1. Board lanes are ordered by database id

Reported as: *"yesterday I used a task, so when today I go and search, in Paused it will be at
last."*

`kra.kpi` declares **no `_order`**, so Odoo falls back to `id` ascending and every lane reads
oldest-at-top. Nothing sorts them afterwards — `groupIntoLanes` sorts exactly one bucket, `today`,
by `today_seconds`.

The trap is that the obvious fix does not work. Sorting by `id` descending is still creation order,
so a task opened months ago and worked yesterday stays near the bottom — which is the reported case.
The order has to follow **activity**, and no field in `/kra_kpi/tasks/get` carries it:
`timer_start_datetime` is cleared on pause, `timer_total_seconds` is a lifetime figure, and
`today_seconds` is 0 for anything older than today. One server field is the whole dependency, and it
is derivable from `kpi.time.log` with a single `read_group` for the entire board — the same shape
the `today_map` block already uses, and it needs **both** `start_time:max` and `end_time:max`
(worked A 09:00–17:00 and B 10:00–10:30, and `start_time` alone ranks A as older).

Two things make this cheap once the field exists. `groupIntoLanes` is the only place the app groups
tasks, and both the grid and list views read `lanes[laneKey]`, so one comparator covers both. The
web board's `kpi_action.js` has the identical `groups.today.sort(...)` line, so the same comparator
keeps the two boards in step.

Also worth knowing: the Today lane already exists **for this exact complaint** — its comment says
"one paused ten minutes ago looks identical to one paused three weeks ago". Today only covers today.
Yesterday's task was always going to fall through it.

## 2. Standalone reminders — designed, and bigger than it looks

A reminder that is not attached to a task: name, date, time, and the phone rings like a clock alarm.

The app can already do the hard part. `scheduleTaskAlarm` takes an **absolute epoch ms**, arms a
notifee `TIMESTAMP`/AlarmManager trigger with `allowWhileIdle`, loops the sound on the ALARM audio
stream and takes over the lock screen until Stop — and it only ever reads `{ id, name }` off what it
is handed, so it does not care that there is no task. `DurationTimePicker` already has a
`mode="clock"` returning `{ hour24, minute }`, `DateGridModal` gives the date, and a single `QUICK`
entry lands on both the Home grid and the drawer, because they read the same array.

What is *not* free, and is the reason this is not a small feature:

- **Storage is on Odoo, but the ring is on the device.** A row is not an alarm. Anything created or
  edited on the web has to reach a phone before its time or nothing rings. The design is to push
  **when the row is written, not when it is due** — the device then arms an AlarmManager trigger
  that fires at the exact second, offline, with no further network. A cron pushing at ring time
  would be at the mercy of FCM latency and Doze. `_send_push` already exists to build on.
- **That push has to be handled with the app closed**, which the app cannot do today — it only
  registers a *response* listener, which needs a tap. It needs `expo-task-manager`, a native
  dependency, so it costs an EAS rebuild.
- **The on/off switch must not be called `active`.** `active` is Odoo's archive flag: an
  `active=False` record is filtered out of every list and `search()` by default, so switching a
  reminder off would make it vanish instead of showing as off — the opposite of an alarm toggle.
- **A `state` field cannot hold history.** Tick a daily reminder five days running and one `done_at`
  remembers only the last tick, so completions need their own model, with the name and time
  **snapshotted** and `ondelete='set null'` — history that disappears with its reminder is not
  history.
- **The repeat rule belongs in one language.** "+1 day, same wall-clock time, across a DST change"
  written once in Python and once in JS is two implementations that will disagree, and the
  disagreement surfaces as an alarm an hour early, months later. The server owns it and returns the
  advanced row; the app arms whatever comes back.

Settled with the user: stored in Odoo, editable from the web, daily/weekly repeat, a round tick that
completes and logs history, a Samsung-style per-row toggle, and **exactly one** new menu line
(KRA/KPI → My Work → Reminders) with history reached from inside it rather than a second entry.
