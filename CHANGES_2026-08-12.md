# Changes — 12 Aug 2026

Client-flow defects, billing de-duplication, and the display gaps found while testing them.
Everything below was verified against a restored copy of the live database, not just read.

Module released as **19.0.2.9** (from 19.0.2.7).

---

## 1. A client could sign off any task and make it billable

`/kpi_client_approval/approve` wrote the terminal fields from **any** state. A client could
create a task and immediately mark it `completed` + `client_final_approved` — skipping admin
accept, client pre-approval and every minute of developer work.

Proven: task 302 went `assigned → completed` with `admin_accepted = false` and no `REQ-` ref.

Fixed with a state guard in `controllers/kpi_reports_api.py`. It accepts `awaiting_client`
**and** the legacy `partially_completed + admin_approved` shape, because that is exactly what
`/kpi_client_portal/dashboard` still returns in `pending_approvals` — the app renders a
Sign-off button for whatever that list contains, so the two must agree or the button dies.

The web Requests table offered **Sign** for any `partially_completed` row
(`kpi_client_dashboard.js`); that was the only affordance letting a client sign work no admin
had checked. Now gated on `awaiting_client`, and that state finally has a badge colour.

## 2. Invoiced tasks came back on every future invoice

`action_populate_from_logs` built its line set in two passes and **neither excluded
already-invoiced tasks** — `is_invoiced` appeared in no `search()` domain in the module. Pass
2 also had **no date filter at all**, so every signed-off task under a client was swept into
every invoice, forever.

Proven: invoice A (4 tasks, finalised), then invoice B dated **2020-01-01 → 2020-12-31**
returned the same four 2026 tasks. They showed 0.00 only because A was finalised and locked
them — display-level hiding, not exclusion.

Fixed in `models/kpi_client_invoice.py`: exclude tasks already carried by any other invoice
line, and give pass 2 a sign-off date window.

## 3. Two draft invoices billed the same work twice

The "already billed" lock only engages once an invoice reaches `finalized`/`sent`, so two
concurrent drafts each charged full value with nothing to stop them.

Proven: drafts C and D both read **60.00 / 6h** for the same two tasks. Now C carries the
work and D comes back empty.

The fix keys on **invoice-line membership, not `is_invoiced`**, and deliberately not on
dates: `services/ownerDashboard.js` hardcodes `2000-01-01 → 2099-12-31`, so a date-based fix
would never have excluded anything on the owner path.

## 4. Clients could not reject at sign-off

`/kpi_client_approval/reject` called `reject_task()`, which raises unless the task is
`partially_completed`. By sign-off time it is `awaiting_client`, so the call **always** failed
— and a blanket `except` swallowed it. The client saw nothing happen.

Now routed to `record_client_final_decision('reject')`, which walks the task back to `rework`
itself. Proven: `awaiting_client → rework`, `admin_approved` cleared, reason stored as
`🔴 CLIENT REJECTED — …`.

That method returns a **string** status (`'ok'` / `'invalid'`), and both OWL callers test
`if (!r.status)` — every one of those strings is truthy in JS, so a failed rejection would
have shown the success alert. The controller collapses it to a boolean.

## 5. Clients could not see their own invoices

The three client record rules matched only `client_kra_id.client_user_ids`. In practice the
portal user is attached to the **parent** KRA while `client_kra_id` resolves to the **child**,
so the rules found nobody — **89 of 93** stuck tasks looked like this.

Widened to accept a user on the client KRA **or its parent**. One level up is complete, not a
heuristic: `_compute_is_client` only ever flags level 1 and level 2.

Measured on real data: the client's visible scope went from **41 tasks to 215**, and awaiting
sign-off from **4 to 92**.

`security/kpi_client_invoice_record_rules.xml` is `noupdate="1"`, so the XML alone changes
nothing on an existing database — `migrations/19.0.2.8/post-migrate.py` applies it to the live
records. Written against the ORM, not raw SQL: a previous release shipped a post-migrate that
selected a non-existent column and aborted an upgrade mid-run.

## 6. Task description was invisible to admins on mobile

Not a save bug — every creation path stores it (`create_kpi`, the client portal, the web form).
The web was fixed on 11 Aug; that commit touched only `odoo_modules/`, so the app never got it.

- Mobile board: the payload always carried `description` and the app rendered it nowhere. Added
  to the shared detail body, so the kanban card and list row get it together.
- Accept modal (**web and app**): the one screen where an admin decides whether to accept
  showed only the title and requested type.
- Mobile Client Task Queue: the field was hidden unless a description already existed — and it
  is editable, so hiding it removed the only way to add one.

A `plainText()` helper strips tags first: some rows store `<p><br></p>` as "empty", which would
otherwise render as visible markup and count as content.

## 7. Cards did not say which client the work was for

`map_rec` in `controllers/kra_api.py` feeds both the web lane cards and the entire mobile
board, so one field there covers five surfaces. The sibling single-task serializer got it too,
or a card opened from a notification renders blank.

Verified: **281/281** tasks now return a client name.

All 281 also have client and project **identical** — there is no separate project level in use
— so the project line is suppressed when it merely repeats the client.

Placed as a truncating `MetaRow`, not a chip in a header row: the board lane is a fixed 278px
and those rows do not wrap.

## 8. "Start Workday" reappeared after ending the day (web only)

Not a state bug — every flag was already correct, and no duplicate sessions exist in the data
(all 27 multi-session days followed a legitimate *auto*-close).

It was an OWL template binding bug. The green button used `t-else`, which binds to the previous
sibling carrying a `t-if` — and that sibling is the **admin-only Reopen** button, not the
"Workday ended" button above it. So the condition was effectively `not (dayDone and isAdmin)`,
which is why only **developers** saw it. The button was dead too: `/kpi_workday/ping` refuses
with `day_done`.

Introduced by the 11 Aug commit that inserted Reopen between the two. Now an explicit
`t-if="!state.dayDone"`, so inserting anything else cannot rebreak it.

## 9. Mobile: clients can now reject, and failed sign-offs are visible

- Added a **Request changes** button beside Sign off, reusing the existing reject-reason sheet
  (made stage-aware rather than duplicated — stage 1 refuses *who* was assigned, stage 2
  refuses the *delivered work*, and they hit different endpoints).
- A failed sign-off showed the client nothing: the modal stayed open while the toast rendered
  outside it, and an RN Modal is its own native window. The error now appears inside the sheet,
  which also preserves the name they typed.
- Buttons are stacked full-width, not side by side — "Request changes" does not fit a
  half-width button at 360dp.

## Verification

Two re-runnable scripts, both against a restored copy of the live database:

- `node scripts/e2e-client-flow.mjs` — **27/27**. Walks a task through all four gates and
  checks the wrong actor is refused at each one.
- `node scripts/e2e-billing-dedup.mjs` — **3/3**. Isolates the two billing defects on a fresh
  client tree so an already-finalised invoice cannot mask the result.

Also: `npx jest` 49/49, every changed screen parsed with `babel-preset-expo` (`node --check`
does not catch JSX in this repo), and `odoo.log` scanned from a byte offset — no errors for
the target database.

A re-run caught a flaw in the harness itself: a near-copy of the drive-to-sign-off helper had
drifted (no progress summary), so `complete` failed silently and the reject probe asserted
against a task still in `in_progress` — passing for the wrong reason. The duplicate is gone;
one helper now takes a `stopBeforeSignoff` flag.
